# Known issues

Status as of 2026-09-19, describing v0.7. Every row says which surface it
belongs to. **All known functional bugs resolved.**

Four surfaces, because a limit almost always belongs to exactly one of them:

| Surface | What it is | Where its limits are |
|---|---|---|
| **Explicit functions (`v0.4.0` – `v0.6.0`, unchanged in v0.7)** | `gpu_sum` / `gpu_min` / `gpu_max` and the `gpu_*_resident` surface — uploads, fused joins, GROUP BY / top-k — called by name from SQL. This surface needs nothing but a DuckDB client | the v0.3.0 – v0.6.0 tables below |
| **The transparent path (v0.7)** | ordinary DuckDB SQL through the `gpudb` shell or the Python wrapper's `gpudb.connect()`: a statement is answered on the device when that is faster and by DuckDB otherwise, with identical rows, names and types | the v0.7 tables below |
| **CUDA** | the explicit functions, complete; and the exact operators the transparent path needs — exact `GROUP BY`, the `WHERE` mask, the global aggregate and the materialised join — are implemented and **on by default**. `GPUDB_CUDA_EXACT=0` turns them off: the backend then reports `exact_supported()` / `join_supported()` / `global_supported()` false and the wrapper leaves every statement on DuckDB, which is correct and simply has no speed-up. This needs a binary that carries CUDA — the registry's Linux one may not, see the row below | `docs/CUDA_EXACT_PATH.md` |
| **The community-registry Linux binary** | built without a CUDA toolchain, so it is CPU-only: every `gpu_*` function works and returns the same results, and `gpu_build_info()` / `gpu_last_stats()` say `backend=CPU`. The registry's macOS binary carries the full Metal backend | `README.md`, `docs/TRANSPARENT_DESIGN.md` §9.4 |

Nothing below is a wrong answer. Every shape the GPU path does not cover runs on
DuckDB: through `gpudb.connect()` that happens by itself and
`con.last_rewrite()["reason"]` says why; from SQL it means writing native
`sum()` / `min()` / `max()` / `JOIN` / window functions for that query.

## Documented intentional divergences from SQL spec

None. The `MIN/MAX/SUM` empty-input / all-NULL → `0` divergence was resolved in
`v0.2.0` (see the resolved table below); those aggregates now return SQL `NULL`,
matching native DuckDB, and `IS NULL` on such a result is now `true`.

### Design notes (v0.3.0)

| Behavior | Reason |
|---|---|
| The SQL aggregate path (`gpu_sum`/`gpu_min`/`gpu_max` called from SQL) does not dispatch to the GPU | Deliberate v0.3.0 design, not a fallback. DuckDB feeds aggregates pre-grouped 2048-row chunks; on unified memory, copying those out to feed a GPU reduction is pure overhead (measured 3×–110× end-to-end loss in v0.2.0 — see BENCHMARK.md). v0.3.0 streams running accumulators instead and reaches parity with native. GPU reductions remain at operator level (`gpudb-bench` etc.); GPU value on the SQL path moves to the join track. |
| Apple GPUs have no IEEE-754 double precision in MSL | Still true and still relevant to operator-level f64 work on Metal (runs on host there). No longer affects the SQL aggregate path (see row above). |
| `GPUDB_FORCE_BACKEND` no longer affects SQL aggregates | The env var routed the deleted buffered/batched path; it is a silent no-op on the aggregate path as of v0.3.0. Operator-level tools still honor backend selection. |

### Design notes — resident-column surface (v0.4.0)

| Behavior | Reason |
|---|---|
| `gpu_sum_resident` (and the streaming `gpu_sum`) wrap on int64 overflow where native `sum(BIGINT)` promotes to `HUGEINT` | The GPU kernels and the C ABI accumulate in 64-bit; wrap is two's-complement (uint64 accumulate — defined behavior, identical on CPU/CUDA/Metal). Use native `sum()` if your column can exceed int64. |
| One `gpu_upload` call = one column name; a name column with mixed values errors | Values from different names silently merging into one column is data corruption; use a constant name or `GROUP BY` the name column. |
| `gpu_upload` names may not be NULL; read-side NULL names yield SQL `NULL` rows | Upload with NULL name used to silently register the column under `''`. |
| Total memory buffered by in-flight `gpu_upload` states is capped (default 4 GB, `GPUDB_UPLOAD_POOL_MAX_MB`) | `gpu_upload` inside a running window frame buffers O(n²) (combine per output row) and would otherwise OOM the host from a KB-scale input. The cap turns that into a clean error. |
| An unreferenced `gpu_upload` subquery column is pruned and the upload never runs | DuckDB's unused-column elimination; always reference the upload count in the outer query (see `src/extension/gpu_resident.cpp` header). |
| Resident f64 columns run on the host on Apple Silicon (`reason=Resident_OnCpu`) | No IEEE-754 doubles in MSL. The host path is parallel (chunked reduction) as of v0.4.0 — measured faster than a native DuckDB scan on M4 Max — and f64 sums are deterministic per upload, not per dataset (parallel upload order affects rounding, same as native). |
| Whole-column `gpu_min_resident`/`gpu_max_resident` are slower than native `min()`/`max()` on unfiltered persistent tables | Native answers those from zonemap statistics without scanning — a metadata lookup no engine can beat. The resident path wins where a real reduction happens (sums, or data DuckDB has no stats for). |

### Design notes — fused resident joins (v0.5.0)

| Behavior | Reason |
|---|---|
| Join keys must be `BIGINT` resident columns; payloads may be `BIGINT` or `DOUBLE` | The v0.5 join ABI is single-column i64 equi-join. `DOUBLE`/`DECIMAL`/`VARCHAR` keys, composite keys, and non-equi joins are not on this ABI — write them as native `JOIN`s, or use the transparent path's joins (v0.7 table below). |
| `gpu_upload` skips NULL values and `gpu_upload_pair` skips a row when **either** its key or its payload is NULL — resident columns carry no NULLs | There is no validity mask on the device. Consequences: `gpu_join_*_count_resident` counts non-NULL rows only, LEFT / ANTI never emit NULL-key probe rows, and (v0.6) `gpu_groupby_*_resident('p')` equals native `SELECT k, sum(v), count(v) FROM t WHERE k IS NOT NULL AND v IS NOT NULL GROUP BY k` — no NULL-key group, `count` is `COUNT(payload)` not `COUNT(*)`, a key whose payloads are all NULL is absent (native returns `(k, NULL, n)`), and top-k never returns NULL rows. Filter or `coalesce` before upload if the native semantics matter. **v0.7 exact path:** `gpu_upload_pair_exact(name, k, v)` keeps both NULL kinds and `gpu_groupby_exact_resident[_having\|_topk]` returns `(key, sum HUGEINT, count, count_star, min, max, avg)` with native semantics — NULL-key group last, `count(*)` includes NULL payloads, all-NULL group gives NULL sum/min/max/avg, the sum never wraps (test/sql/gpu_groupby_exact.test checks it against native both ways). Implemented on CPU (the reference), on Metal and on CUDA, on by default on both GPUs; started with `GPUDB_CUDA_EXACT=0` these functions fall back to the CPU backend. The legacy functions are unchanged. The WHERE mask (§4.6: `gpu_upload_rows_exact` + `gpu_groupby_exact_resident_where[_having\|_topk]`, conjunctions of comparisons / `in` / `is [not] null` over row-aligned predicate columns, DOUBLE under DuckDB's total order) runs on CPU (the reference) and Metal — on Metal a key comparison becomes a binary-search range on the sorted cache, the remaining terms a per-row mask, and the reduce either skips masked rows in place or first compacts the sorted permutation to the survivors, chosen per call by the surviving fraction (`GPUDB_METAL_MASK_COMPACT_BELOW`, default 0.5, until the gate sweep fixes it; the reduce has a second level (blocks of 256 chunk partials) so a group spanning millions of rows is not merged by one thread — 7 groups over 6M rows went from 6.1 to 1.1 ms of kernel time, bit-identical since the 128-bit merge is associative; `GPUDB_METAL_TRACE_EXACT=1` prints per-stage GPU times; top-k over at most `GPUDB_METAL_HOST_FILTER_BELOW` groups, default 65536, is a host pass over the shared-memory tuples — 2.1 vs 4.3 ms at 10K groups — and the device radix select above); on CUDA the same mask runs by default, and under `GPUDB_CUDA_EXACT=0` `_where` calls fall back to CPU there. The exact table functions support projection pushdown: only the columns a statement reads are produced, which matters when millions of groups come back. |
| An upload whose input yields zero non-NULL rows (or pairs) registers nothing and does **not** replace a previously uploaded column of the same name | The upload aggregate never sees a row, so finalize has nothing to register; the old column stays. Pipelines that refresh a name should `gpu_drop_resident(name)` (both `name.k` and `name.v` for pairs) first, or check the upload's returned row count. |
| Keys and payloads must be uploaded together with `gpu_upload_pair(name, key, payload)` — registers `name.k` and `name.v` | Two separate `gpu_upload` calls over a parallel scan do not preserve row alignment between key and payload (DuckDB scans chunks in parallel); a misaligned pair silently sums the wrong rows. `gpu_upload_pair` interleaves both in one scan. |
| `gpu_join_sum_resident` returns SQL `NULL` when no rows join; `gpu_join_count_resident` returns `0` | Matches native `sum()` / `count(*)` over an empty join. |
| INNER and LEFT carry full build-side multiplicity (a probe row joined to 3 equal build keys contributes 3×); SEMI/ANTI contribute each probe row at most once | Native join semantics. `matched` in `gpu_last_stats()` counts the rows contributing for that kind (ANTI counts non-matching probe rows). |
| RIGHT / FULL OUTER are compositions, not separate functions | Probe-payload sum equals INNER / LEFT respectively; the missing-side `COUNT(*)` term is `gpu_anti_join_count_resident` with the sides swapped. |
| `DOUBLE` join sums are compared to native within a relative tolerance (1e-9 contract; measured ≤ 1e-11 on both backends), never bit-for-bit | Summation order differs per backend (CUDA: on-device atomics; Metal: GPU multiplicity + host stream). `BIGINT` sums are bit-exact on both. |
| On Apple Silicon the `DOUBLE` payload reduction runs on the host after the GPU computes per-row multiplicity ("GPU searches, host streams") | No IEEE-754 doubles in MSL. Still 5–6× faster than native at SF50 because the random-access part is on the GPU and the host pass is a sequential stream. |
| `gpu_join_rows_resident` (row-returning) wins modestly on unified memory (1.16× at 60M pairs on M4 Max) and **loses to native on discrete GPUs** (0.5× on RTX 4090: ~96% of wall is the ~960 MB device→host copy) | Materialising 60M index pairs across PCIe costs more than DuckDB's native hash join. Use the fused aggregate variants on discrete GPUs; the rows function is the composability primitive for unified-memory machines. Output capped at `GPUDB_JOIN_ROWS_MAX_M` (default 100M rows) with a clean error. |
| The build side's sorted-key + permutation cache (16 bytes per build row) lives on the device outside the `GPUDB_UPLOAD_POOL_MAX_MB` accounting | Device OOM surfaces as a clean `runtime_error` on the first join call rather than at upload. |
| TPC-H SF50-scale pair uploads need `GPUDB_UPLOAD_POOL_MAX_MB` raised (10–12 GB) | Default 4 GB pool refuses with the documented error; same guardrail as resident columns. An EXACT upload has its own cap instead (`GPUDB_EXACT_UPLOAD_POOL_MAX_MB`, default half of physical memory). |
| `gpu_join_rows_resident` needs the uploads to run as earlier statements (`gpudb-sql --multi`, or separate statements on one connection) | A table function's bind/init cannot be sequenced after an upload in the same statement. The scalar join-aggregate functions have no such restriction. |
| `probe_idx` / `build_idx` from `gpu_join_rows_resident` refer to **upload order**, which equals table order only when the upload scan was not parallel | Same ordering caveat as any parallel scan; use the indices to look up rows, not as row numbers of the source table. |
| The explicit v0.5 join functions answer one equi-join per call and have no `GROUP BY` over the join's result | Composition is not theirs to do. From SQL, chain them with the v0.6 resident GROUP BY functions or write the chain natively. Multi-table join chains and `GROUP BY` over a join's result *are* on the GPU path through the transparent path (v0.7, §4.8 device key joins and §4.13 uploaded joins — v0.7 table below); that is the wrapper's work, not these functions'. |

### Design notes — resident GROUP BY / top-k (v0.6.0)

| Behavior | Reason |
|---|---|
| `gpu_groupby_sum_resident_f64_having` / `_f64_topk` filter on the host, not the device | `DOUBLE` sums are finished on the host on Metal (no doubles in MSL) and the filter runs there through the reference implementation; the saving is only the row streaming (measured 1.4–2.6× vs native, against 5–8× for the BIGINT HAVING forms and 4× for BIGINT top-k on Metal). CUDA filters f64 on the device. |
| `_topk` tie order is unspecified | When several groups share the k-th aggregate, which of them are returned — and in what order among equals — is backend-defined (Metal/CPU: key ascending; CUDA: radix-sort order). An `ORDER BY` on the result fixes only the order among the returned equals; if *which* tied groups come back matters, ask for k plus the expected ties, or use the `_having` form and rank in SQL. Cross-backend checks compare multisets. This is the contract of the **explicit** function, and it is deliberately not the transparent path's: a plain `ORDER BY … LIMIT k` that ties declines with `ties` and DuckDB answers it — the row in the transparent-path table below. |
| Metal `_topk` with k close to the group count is slower than the plain form + `ORDER BY` | The Metal top-k always runs the 8-pass radix select and then orders the k rows on the host; for k a large fraction of the groups that host sort dominates. CUDA switches to a full device sort for k > groups/8. On Metal use `gpu_groupby_sum_resident` + SQL `ORDER BY … LIMIT` when k is not small. |
| The first filtered call on a backend allocates device scratch for the finalized groups | 24 B per group (1.8 GB at 75M groups) allocated once and reused by every later filtered call on any pair; the first (B′) statement at SF50 on Metal took 0.9 s, later ones 78 ms. Counted in the process's device memory, outside `GPUDB_UPLOAD_POOL_MAX_MB`. |
| Every Metal device allocation made before v0.6.0 (resident columns, sort caches, scratch) was never released — `gpu_drop_resident` freed the host-side accounting but not the GPU buffer | The Metal host code was compiled without ARC; v0.6.0 turns it on (`-fobjc-arc`), so dropped columns and their caches now release device memory. Long-lived processes on v0.5.0 that upload/drop repeatedly grow until restart. |
| `gpu_groupby_*_resident` / `gpu_topk_resident[_f64]` are table functions; the uploads they read must run as earlier statements on the same connection | A table function's bind/init cannot be ordered after an aggregate in the same statement (a single cross-product reference happens to work, two do not — DuckDB's pipeline ordering gives no guarantee). The result types are fixed per function (`_f64` variants) for the same reason: bind cannot inspect a column that a same-statement upload has not produced yet. |
| Rows come out sorted by key ascending on every backend | The GROUP BY is a sort + segmented reduce over the cached radix sort (the join build cache), so order is free and cross-backend parity is a plain row diff. Need a different order? `ORDER BY` the result — it is small. |
| `sum` of a `BIGINT` payload wraps on int64 overflow where native `sum()` promotes to `HUGEINT` | Same uint64 wrap rule as `gpu_sum_resident` and the join sums; bit-identical on CPU/CUDA/Metal. Use native `sum()` if a group can exceed int64, or the v0.7 exact path (`gpu_upload_pair_exact` + `gpu_groupby_exact_resident`, HUGEINT sum, see the NULL row above). |
| `DOUBLE` group sums compare to native within a relative tolerance (1e-9 contract), never bit-for-bit; on Apple Silicon they run on the host after the GPU sorts and gathers | Summation order is backend-defined; no IEEE-754 doubles in MSL. Same rule as the f64 join. |
| Top-k tie order among equal values is unspecified | Same as SQL `ORDER BY` without a tiebreaker; the sort is not stable across backends. Cross-backend checks compare the multiset of values, not `idx`. Again the explicit function's contract only — see the `ties` row in the transparent-path table. |
| Group count is capped at `GPUDB_GROUPBY_ROWS_MAX_M` million (default 100) with a clean error naming the actual count | Checked before any device→host copy on every backend, never truncated — the same guardrail as `GPUDB_JOIN_ROWS_MAX_M`. |
| The sort cache costs 16 bytes per row per sorted column on the device (sorted keys + permutation), outside the `GPUDB_UPLOAD_POOL_MAX_MB` accounting; on Metal the radix sorter additionally keeps its ping-pong scratch (32 bytes × the largest row count sorted so far) for the life of the process, on CUDA the sort scratch is transient | Built lazily on the first GROUP BY / top-k / join-build use of a column, shared by all of them, freed with the column. Device OOM surfaces as a clean error on that first call (CUDA: `cudaMalloc join cache (sorted keys) failed: out of memory`). Worked example: at SF50 two resident pairs (4.8 GB each) plus one sort cache do not fit a 16 GB GPU — `gpu_drop_resident` what you no longer need. (On the v0.7 exact path a lane is stored at the narrowest width its values fit and the sort cache follows it — `docs/RESIDENT_COLUMNS_DESIGN.md` §6 — so these figures are the v0.5/v0.6 columns'.) |
| `gpu_groupby_*_resident` / `gpu_topk_resident*` results reflect what was uploaded: a NULL key or NULL payload row was never uploaded (see the v0.5 table above) | Same rule as every resident op; stated here because native `GROUP BY` would show a NULL group and `count(*)` would include NULL payloads. Test 14 in `test/sql/gpu_groupby_resident.test` pins the behaviour; the v0.7 exact path (`gpu_upload_pair_exact` + `gpu_groupby_exact_resident`) keeps the NULLs and matches native. |
| ~~On CUDA, a device fault raised inside a Thrust call aborted the process instead of surfacing as a SQL error~~ | **Resolved in v0.6.0**: the resident CUDA paths run CUB primitives on explicit temp storage (no Thrust temporaries), so a sticky device fault is mapped to a `runtime_error` naming the CUDA error and the statement fails cleanly; pinned by a unit test that re-executes the binary with a fault-injection hook and checks the child exits normally. Linux + CUDA only. |
| Low-cardinality GROUP BY over a `BIGINT` key differs between backends: CUDA wins with the data resident (7 groups at SF10: 31 ms native vs 5.9 ms), Metal loses (4 groups at SF10: 31–35 ms native vs 47 ms) | Both run the same sort + segmented reduce; on Metal the gather of every value through the sort permutation is the cost and there is no fp64/atomic hash path to fall back to. Native's streaming aggregate is scan-bound and very fast at low cardinality. Rows in BENCHMARK.md. (The v0.7 exact path answers few-group keys with the direct grouped reduce instead — v0.7 table below.) |
| On discrete GPUs (CUDA) the device→host copy of the `(key, sum, count)` result dominates wall time for high-cardinality outputs (24 bytes/group); the kernel is a few percent of wall | Same honest split as `gpu_join_rows_resident`. `gpu_last_stats()` shows `kernel_ms` vs `wall_ms`. On unified memory (Metal) there is no copy: the GPU writes the result vectors in place. |
| Low-cardinality GROUP BY (a handful of groups over tens of millions of rows) is not the target shape for these v0.6 functions | The sort is wasted work there; native's streaming aggregate is scan-bound and very fast. Measured rows for both shapes are in BENCHMARK.md — pick by cardinality. |

### Design notes — the resident registry

| Behavior | Reason |
|---|---|
| A resident set is one registry entry: `gpu_upload_pair('p', …)` makes the set `p` with columns `p.k` / `p.v`; `gpu_drop_resident('p.v')` drops the whole set, and re-uploading under a name replaces the set | The transparent path needs set-level state (ready / stale / epoch / references) shared by both columns; a half-dropped pair could otherwise be ranked by its surviving key (test 17 in `gpu_groupby_resident.test`). Column-name resolution (`'p.k'`, `'p.v'`, bare `'c'`) is unchanged for every operator. |
| Names starting with `gpudb:` are reserved for identity tags `gpudb:v1:<catalog>:<schema>:<table>:<table_oid>:<columns>[:<extra>]` (fields may not contain `:`, the column list not `,`; `<extra>` is opaque) — a name with the prefix that does not parse is an upload error | The tag is what the wrapper keys managed sets by (docs/TRANSPARENT_DESIGN.md §5.3); the extension parses it so `gpu_residents()` can show identity and so a user cannot create a `managed` set by accident. Everything else is an `explicit` set. |
| Managed sets are prepared at upload (`state = ready`); explicit sets keep the v0.6 lazy build (`state = uploaded`) until an operator or `gpu_prepare_resident()` runs | On CUDA the sort cache of a 60M-row key column takes ~50 ms and 16 B/row of device memory; explicit users of `gpu_sum_resident` alone would pay it for nothing. A managed set's first hit must not pay it (§5.5). |
| `gpu_assert_rows(name, n)` compares `n` against the rows the upload scan *delivered* (`rows_seen`, NULL rows included), not the rows resident | The guard is meant to receive `count(*)` of the source table; NULL keys/payloads are skipped at upload, so the resident row count would mismatch on any table with NULLs. Upload from the whole table (no `WHERE`) or the guard will always raise. |
| The guard must be a one-row derived table cross-joined to the resident call and referenced in `WHERE` (`… r, (SELECT gpu_assert_rows(tag, count(*)) AS ok FROM t) gd WHERE gd.ok`) | A guard in the outer `WHERE` is never evaluated when the resident result is empty (a stale empty answer would pass); an unreferenced derived column is pruned by the optimizer. The derived-table-plus-`WHERE` form runs exactly once whatever the left side returns (test 11 in `gpu_resident_registry.test`). Errors carry the prefix `GPUDB_STALE:`; a wrapper re-runs natively on that prefix only. |
| `gpu_invalidate(pattern)` matches the exact name or names starting with `pattern` followed by `:`; an upload that started before the invalidation and finishes after it is discarded with `GPUDB_UPLOAD_DISCARDED:` | Prefix matching lets one call invalidate every set of a table; the discard closes the window in which a background upload read a snapshot that a write has since changed (§5.5 epoch capture). Explicit sets are never invalidated unless asked. |
| A dropped or replaced set's device memory is released when the last operator call using it returns, not at the drop | Operators hold a reference instead of the registry lock, so a query on one connection never blocks an upload or a drop on another; `gpu_residents().refs` shows calls in flight. |
| One resident registry per DuckDB database (per `LOAD`), not per process | Two databases open in one process, or an `ATTACH`, cannot cross-serve a same-named set. `gpu_last_stats()` is per database; the per-set copy is `gpu_residents().last_stats`. |
| `GPUDB_UPLOAD_POOL_MAX_MB` counts *logical* bytes: a state that combined another state's buffer is charged for it although the segments are shared, not copied | The cap exists to stop `gpu_upload` inside a window frame from buffering O(n²); sharing the segments removed the copy but the guardrail keeps its meaning. Reservation is per 2048-row chunk, so two threads can overshoot the cap by a chunk each. |
| A concurrent upload still slows a native statement on another connection of the same database for as long as it runs — the same 1.3–2.4× at p99 that any native aggregate over the same columns costs | One DuckDB process is one worker pool; the extension takes no lock in the scan and does no per-row atomics any more (that cost 3–7×), so what remains is DuckDB's scheduling. `scripts/residency_gate.sh` compares the upload against DuckDB's own `list()` as the control; a wrapper's quiet period / rate cap decides *when* to upload (§5.5). |
| **A background upload on a machine whose cores are already taken still costs a sub-millisecond statement about 0.1 ms at p99.** The two steps an interrupt cannot stop now wait for a quiet connection first, which takes the residency gate's `small_scan` from a median 0.82× (3 failures) to 0.99× (none) with 8 of 16 cores busy; the shortest shape of all, `point_lookup`, goes from 0.43× to **0.79×** and still does not pass | What is left at that resolution is p99 0.5 ms against a control of 0.4 ms — 0.1 ms on a 0.4 ms statement, where the gate's tolerance is 10%, i.e. 0.04 ms. It is the segment scans themselves (about 58 of them, ~6.8 ms each, each interrupt honoured in ~0.27 ms) and the mere existence of a worker thread: a thread with the uploader's wake pattern and no DuckDB work at all measured p99 0.68 ms against controls of 0.46 / 0.71 ms. Deferring the segments too would remove it and would also mean a session that never uploads, which is no feature at all, so the shape is published rather than tuned away. The price of the back-off is stated with it: on a loaded machine the set becomes resident about 2.5× later (measured, 4.8 s into the pass against 0.57 s after it), in exchange for no statement of the run paying for it, and no step hit the 20 s deadline in any of the 50 loaded passes. Idle time-to-ready does not move. `docs/TRANSPARENT_DESIGN.md` §5.5, §9.3. |

### Design notes — upload sessions

| Behavior | Reason |
|---|---|
| Between `gpu_upload_begin(name)` and `gpu_upload_finish(name)`, every `gpu_upload`/`gpu_upload_pair` statement for that name **appends a segment** to the session and returns its own row count; no device memory is touched until finish | The wrapper uploads a table as short row-id-range statements so an upload never runs a long scan beside a user query (docs/TRANSPARENT_DESIGN.md §5.5/§5.6). `gpu_upload_status(name)` returns the open session's segment/row/byte counts as JSON. |
| A segment statement that fails or is interrupted before finalize leaves the session exactly as it was; the wrapper re-runs that segment and keeps the earlier ones | The append is one step under the registry lock at finalize; a scan interrupted between vectors never reaches finalize. Registry test cases 24–32 pin begin/append/finish/abort/kind-mismatch/re-begin/invalidate. |
| All segments of one session must use the same upload function and column types (all `gpu_upload_pair`, or all bare `gpu_upload`); a mismatch is an error and does not corrupt the session | One session builds one set; mixing a pair segment with a bare-column segment has no meaning. |
| `gpu_invalidate` (and any epoch bump) drops an open session and frees its buffers; `gpu_upload_finish` then raises `GPUDB_UPLOAD_DISCARDED:` | A write that lands mid-upload must not produce a set built from a stale snapshot; the wrapper re-begins after the quiet period. Same epoch rule as a single-statement upload. |
| The host buffer cap (`GPUDB_UPLOAD_POOL_MAX_MB`) counts a session's held segments; `gpu_upload_abort(name)` or a re-`gpu_upload_begin(name)` releases them | A session holds the whole table in host memory until finish, so it is charged like any buffered upload. |
| A session's segments come from one connection's statements; the upload connection cannot see another connection's temp tables | DuckDB temp objects are connection-local; the wrapper's resolver already declines temp tables, so they are never uploaded. |

### Design notes — the statement rewriter (extension side)

These rows are about the pure C++ matcher `gpu_rewrite_ast` in the extension.
They are **not** a statement of what the transparent path can answer: the Python
wrapper normalises a statement before handing it over (see the v0.7 transparent
table below).

| Behavior | Reason |
|---|---|
| `gpu_rewrite_ast(tree, context)` is pure and not volatile: DuckDB may constant-fold or cache it, and it records nothing | The wrapper evaluates it once per literal-normalised template (docs/TRANSPARENT_DESIGN.md §3.3); a scalar that touched the registry could not be cached and could race with uploads on another connection. Residency, stats, output names/types all arrive in `context`. |
| Everything about residency and exactness is decided from `context`, never from the catalog: `ready`, `backend`, `rows`, `stats` (`has_null`, `min`, `max` from `stats(col)`), `columns` types, `outputs` from `DESCRIBE` | A C-API scalar has no catalog access. A wrong context gives a wrong rewrite; the wrapper is the single place that builds it and the in-statement `gpu_assert_rows` guard is the backstop for row-count drift. |
| On a v0.6 set (`gpu_upload_pair`) refuses (reason `nulls`) unless the context proves both columns NULL-free and (reason `overflow`) unless `rows × max|v| < 2^63`; on an exact set (`"exact": true` in the context, `gpu_upload_rows_exact` / `gpu_upload_pair_exact`) neither gate applies and the rewrite emits `gpu_groupby_exact_resident[_where][_having\|_topk]` with `sum` / `count` / `count(*)` / `min` / `max` / `avg`, a `WHERE` program (conjunctions of column-vs-constant comparisons, `IN`, `BETWEEN`, `IS [NOT] NULL`) and native NULL semantics. `VARCHAR` keys and `WHERE` columns (§4.5) are resident as `hash64()` of the text: a key tuple with any `VARCHAR` component is uploaded as one text (`<byte length>:<text>` per component, `N` for NULL) whose hash is the key, with the texts kept in a dictionary that `gpu_resident_dictionary(tag, n)` returns and the rewritten statement `LEFT JOIN`s to put the components back (typed as native, mixed integer / date / string tuples included); a `VARCHAR` predicate column is a hashed lane compared against the hashed literal (`=`, `<>`, `IN`, `IS [NOT] NULL` — no ordering comparisons). Two different strings with one 64-bit hash are detected at upload (the set is refused) and at WHERE resolution (the statement declines), so a collision can never change an answer. Only under binary collation: a non-binary `default_collation` or a `COLLATE` in the table's DDL declines (`collation`). `GROUP BY` over two or three integer / `DATE` / `TIMESTAMP` columns is packed into one BIGINT key at upload (mixed radix from the columns' `stats()` bounds, one slot per column for NULL) and unpacked in the rewritten select list, so the rows, NULL groups and output types are native's; the components' `GROUP BY` order must be the set's, and a `WHERE` on a component reads it as a predicate lane; when the ranges do not fit in 64 bits the shape runs native. `DATE` and `TIMESTAMP` columns work as the key and as `WHERE` columns (resident as days / microseconds since the epoch, the key comes back typed `DATE` / `TIMESTAMP`); their constants must be plain literals (`DATE '1995-01-01'`, `TIMESTAMP '2020-01-01 12:00:00.5'`) — `DATE '…' + INTERVAL …`, time zones and a constant of the other temporal type decline (`shape`), since the parse tree holds those unevaluated. Always refuses `DOUBLE`/`FLOAT` payloads (`double`), and `DECIMAL` wider than 18 digits (`decimal`); `avg` over a DECIMAL(p ≤ 18, s) is derived in SQL as `double(unscaled sum) / (count × 10^s)`, and is only offered where that is native's own arithmetic: the shape declines (`shape`, detail naming long double) unless `gpu_build_info()` reports `avgf=53` | The v0.6 operators skip NULL rows and wrap int64 sums; the exact operators keep NULLs and sum in 128 bits, so rule 2 holds without the gates. The wrapper chooses the exact path when `gpu_build_info()` reports `exact=true` (and lowers key joins only when it also reports `join=true`) (the GPU backend runs it; on a backend without it the exact ops would fall back to the CPU reference, which rule 1 forbids). Native `avg(DECIMAL)` is not `sum::DOUBLE / count` bit for bit — it is one division by the scaled count, `double(unscaled sum) / (count × 10^scale)`, which both rewrite engines emit (verified against native on millions of rows; the other obvious formulas differ on 20–30% of groups). DuckDB finalises that quotient in `long double`, which is a plain `double` on arm64 (53-bit mantissa) but 80-bit on x86-64 (64-bit), and SQL has no wider type to divide in: once a group's unscaled sum passes 2^53 the two round apart (measured on x86: 982 of 5000 groups over a DECIMAL(18,2) payload, 4M rows). So on x86 the wrapper declines every `avg` over a DECIMAL payload — select list or `HAVING` — and the statement runs native; TPC-H Q1 is the one query in the suite this moves off the device there. `scripts/avg_decimal_parity.py` is the reproducer. The permanent fix is a C++ derivation of the column (`native_avg_decimal`), after which the guard goes. |
| `DECIMAL(p ≤ 18, s)` payloads: the wrapper uploads `(v * 10^s)::BIGINT`; the rewrite returns `CAST(sum AS DECIMAL(38-s,0)) * 10^-s` (typed `DECIMAL(38,s)`) and rescales `HAVING` thresholds by `10^s` with `>` floor, `>=` ceil, `<` ceil, `<=` floor | Equal to native bit-for-bit (parity scenarios, incl. TPC-H `l_quantity`); a threshold finer than the payload's scale keeps the comparison exact by rounding toward the side that cannot change the answer. |
| `ORDER BY … LIMIT` is never removed; it is additionally pushed as `_topk` only when it orders by the selected aggregate (by alias, auto-name, expression or ordinal) with an explicit direction (or the connection's `default_order` in `context`) and there is no `HAVING` | Sorting the small result again is trivial and keeps direction, NULL order and session defaults native's problem. |
| **A pushed top-k whose ordering value TIES inside the first k rows is answered by DuckDB, not by the device** (`last_rewrite()["reason"] == "ties"`, shell footer `DuckDB (ties: …)`). This is the TRANSPARENT path only; the explicit functions two tables up keep their "tie order unspecified" contract | `ORDER BY agg LIMIT k` is not a total order, and DuckDB itself has no fixed answer for it: on TPC-H SF1, `SELECT l_orderkey, sum(l_quantity) qty FROM lineitem GROUP BY l_orderkey ORDER BY qty DESC LIMIT 5` (three orders tied at 320.00 for positions 4–5) returned **5 different orderings and 3 different row sets over 20 plain-DuckDB runs** at `threads=16`, on 1.4.5 and 1.5.5, and is stable only at `threads=1`. There is therefore nothing to reproduce, so the statement goes back to DuckDB rather than the device answering with a rule of its own. The rewritten statement asks the device for k + 1 rows and carries a `QUALIFY` that raises when `rank()` and `row_number()` disagree at or above rank k — which covers a tie at the k-th/(k+1)-th boundary and a tie *inside* the top k, where the row set is right but the order is not. Costs one extra row and two windows over k + 1 rows when there is no tie (measured +0.4 ms at SF1). A lazy relation is read after the wrapper has returned, so through `sql()` — the path the `gpudb` shell takes — that guard runs on a side cursor inside the call, which for a pushed top-k is the device pass itself; its verdict is therefore remembered per rendered statement until the resident sets are dropped (any write, DDL, `SET`, foreign write, or a row count that moved), so it costs one device pass per data version rather than one per call. Paid per call it doubled the shape — 17.1 ms against 8.5 ms through `execute()` and 17.7 ms native — which is how PR #164 shipped and what the fix on the same day removed. The tie is decided against the data, not cached as a shape — but the fallback IS a loss (device pass + DuckDB's run against native alone), so it is recorded as one and the template is measured-declined like any other losing template, with the tie named in `detail`; otherwise a statement whose data always ties would be permanently slower than native and rule 1 would never notice. The ordinary re-measure brings it back once the data stops tying (while the tie is there the probe raises and the template stays native), and a write clears the decision outright, so an `INSERT`/`DELETE` that changes the tie takes effect on the next statement. The decline follows the LITERALS: `LIMIT 4` and `LIMIT 5` share a template but not a fate, so a k below the tie keeps the device. An `ORDER BY` that is already total (`ORDER BY qty DESC, k`) is not pushed as a top-k at all and keeps the device path. **Not covered:** a `LIMIT` whose top-k is not pushed (a `HAVING` beside it, an `avg` or temporal ordering value, `ORDER BY count(*)` over a v0.6 sum set) hands every group to DuckDB, which does the `ORDER BY … LIMIT` itself — the same multiset native sorts, so the tie is DuckDB's both ways, but its top-N depends on the order its input arrives in and the device's group order is not the hash aggregate's, so at `threads=1` such a tie can still land differently. `docs/TRANSPARENT_DESIGN.md` §4.24. |
| Rejected by field, not by node: `DISTINCT` / `ORDER BY` inside an aggregate, `FILTER (WHERE …)`, `GROUP BY ALL`, ordinal group references, `ROLLUP`/`CUBE`/`GROUPING SETS`, CTEs in scope, `TABLESAMPLE`/`USING SAMPLE`/`AT`, window functions, `QUALIFY`, set operations, `SELECT DISTINCT`, `PARAMETER` nodes, `HAVING` with `=`/`<>` | Each returns the input tree unchanged with reason `shape` and a `detail`; `test/sql/gpu_rewrite.test` enumerates them (33 cases). Read this as the matcher's tree-shape list, not as a capability statement: `WHERE`, `min`/`max`/`avg` and multi-column keys came off it with the exact path (row above), and the Python wrapper spells `GROUP BY ALL`, ordinals, `ORDER BY ALL` and `SELECT DISTINCT` out into plain keys (§4.21) and rewrites `FILTER` / `count_if` / `bool_and` / `bool_or` into their `CASE` / `min` / `max` identities (§4.19) before the matcher sees the tree, so those statements do run on the device through `gpudb.connect()`. `HAVING` with `=`/`<>` and compound `HAVING` run as a device GROUP BY with the predicate evaluated by DuckDB over the result (§4.11). |
| A one-column tag (`gpudb:v1:…:<oid>:k`, a bare key set from `gpu_upload`) serves count-only shapes through `gpu_groupby_count_resident[_having|_topk]`; `sum` over such a set is `shape` | The most common GROUP BY after `sum` needs no payload column resident at all. |
| `HAVING count(*) …` next to a `sum` in the select list uses the SUM function's `(key, sum, count)` rows and puts the count predicate in the outer `WHERE` (`gd.ok AND r.count > n`) | No device form filters on count while returning sums; the filter runs on the small result, so rows, names and types stay native's. |
| The rewrite costs ~0.14 ms per matched statement and ~0.045 ms per rejected one (4000 distinct trees, one thread, RTX 4090 Laptop host); `json_serialize_sql` itself is ~0.012 ms | Paid once per template by the wrapper's cache; the parse/dump of a ~5 KB tree dominates. |

### Design notes — the transparent path (v0.7; the `gpudb` shell and the Python wrapper)

`gpudb.connect()` and the `gpudb` shell over ordinary DuckDB SQL.
`con.last_rewrite()` names the reason for each limit below; the reason codes
are in `python/gpudb/connection.py` (`REASONS`).

| Behavior | Reason |
|---|---|
| **Statements that stay on DuckDB by design.** Window functions; `FULL` joins; `SEMI` / `ANTI` **join syntax** (the `EXISTS` / `IN` *forms* are rewritten — §4.18 lowers them to predicate lanes); cross products, including an implicit one with no join condition; more than six tables in one FROM; a join whose result is more than four times its largest table; `sum` / `avg` over `DOUBLE` or `FLOAT` | §2 and §4.7 of `docs/TRANSPARENT_DESIGN.md`. Native `sum(DOUBLE)` is order-dependent — the same table gives different last-ulp results across thread counts and insert orders, and one ulp flips a `HAVING` or a top-k tie — so "same as native" is not definable for it and v0.7 does not rewrite it. `min` / `max` / `count` on DOUBLE are exact and are rewritten. §10 lists each of these with the reason it stays on DuckDB. |
| **Statements that stay on DuckDB**, each because there is no kernel or decomposition behind it: `median`, `stddev`, quantiles; two different DISTINCT columns in one statement; `avg` beside a `DISTINCT` aggregate; subqueries in the select list and in `HAVING`; a subquery that reads another subquery (TPC-H Q2, Q20) | The open-questions list at the end of `docs/RESEARCH_NOTES.md` keeps these with their reasons; WHERE-term subqueries are done (§4.18), and Q22 now runs on the device at every scale factor since the row floor counts the table its lane reads (§4.23). |
| **Keys and payloads that decline.** `UBIGINT` / `HUGEINT` keys (not int64-orderable, §2); a `VARCHAR` key under a non-binary collation — a `NOCASE` `default_collation` or a `COLLATE` in the table's DDL (`collation`); `DOUBLE` keys; `DECIMAL` payloads wider than 18 digits (`decimal`) | The device key is a signed 64-bit value or the hash of a text under binary collation; a collated comparison is not that hash's order. `groupby_parity_check.sh` runs a `NOCASE` VARCHAR key as a scenario that must **not** rewrite. |
| **Syntax left as written** (`shape`): `ROLLUP` / `CUBE` / `GROUPING SETS`, `QUALIFY`, `DISTINCT ON`, `SELECT *`, an ordinal past the select list | §4.21 normalises DuckDB's shorthand (`GROUP BY ALL`, group and order ordinals, `ORDER BY ALL`, `SELECT DISTINCT`, `A RIGHT JOIN B` → `B LEFT JOIN A`) before the decision, and stops there. |
| **Statement-level declines**, before any shape is looked at: prepared-statement parameters (`params`), several statements in one string (`multi`), a statement issued inside an explicit transaction (`transaction`), a statement longer than 16 KB (`too_long`), a set operation (`UNION`, `EXCEPT`, `INTERSECT`) as the whole statement (`shape`), a name that does not resolve to exactly one base table — a temp table shadowing a base table, a view outside the current schema, no hit at all (`temp` / `ambiguous` / `view` / `not_found`), `transparent=False` or `residency='manual'` (`off` / `manual`), and a CPU-only backend (`backend`) | `docs/TRANSPARENT_DESIGN.md` §5.1 (resolution), §5.2 (classification, including the `TRANSACTION` rule), §6. A `UNION`'s arms are each offered to the ordinary path on their own (§4.14), so the statement still runs partly on the device; the set operation itself never is. A correlated subquery does not bind on its own, so it declines by itself (§4.14) — TPC-H Q2 and Q20 are that shape. A CTE has no identity of its own either: only a single CTE that *is* the FROM is folded into the statement (§4.16), and the fold requires that no other part of the statement reads it (`python/gpudb/_flatten.py`), so a CTE referenced twice is left as written. TPC-H Q15's `revenue` CTE aggregates, so §4.14 answers it once and DuckDB reuses that one result; it is on the device at SF1 and SF10 under the inner-statement bounds (§4.23). |
| **Size thresholds.** Tables below `floor_rows` (default 1,000,000 rows) are never parsed — and the floor counts the largest table the statement's answer depends on, including one that only a §4.18 subquery lane reads. Above it every FORM has bounds of its own, from `python/gpudb/_thresholds.py` (Metal's table, swept by `scripts/transparent_gate.py` on TPC-H SF1; CUDA uses the same one). [The size bounds, form by form](#the-size-bounds-form-by-form) below is the whole of it. The selectivity is one `count(*)` scan at decision time, cached with the template; `gpudb.connect(thresholds=False)` disables the table for parity testing | Rule 1: the shapes outside these bounds measured 0.23–0.99× against native (low-cardinality keys, very selective filters, millions of groups pushed back through DuckDB); inside them 1.02–6.2×. The losing rows stay printed in the gate output. The single-table global bound is where a vectorised filter-and-sum stops being memory-bandwidth-optimal on the CPU: 10M × 3 terms 0.93×, 20M × 1 term 0.99× against 30M × 1 term 1.66× and TPC-H Q6 at SF10 2.48×. CUDA uses the Metal table, and since 2026-09-20 that is a measured result rather than a placeholder: `scripts/transparent_gate.py` was run on an RTX 4090 Laptop at the wrapper's own memory budget — 1630 cells, 0 slower than native, 0 differing, minimum ratio 1.07× — and nothing in it asked for a different constant. It is one machine, so the honest statement is verified-on rather than measured-for-every-GPU; TPC-H Q1 straddles 1.0× there and the per-process measured rule is what decides it. |
| **A statement's first execution runs on DuckDB.** When the wrapper first sees a rewritable shape over a table whose columns are not resident, it records the template and runs the statement **unchanged** while the upload proceeds in the background, in short idle row-id segments on a second connection | Rule 1: the first query pays only the round trip, and an upload never runs a long scan beside a user statement (§5.5/§5.6). A session that never goes idle never uploads and runs native throughout — correct, the win is simply not there yet. `residency='eager'` uploads on first sight for scripts that know their workload. |
| **A connection whose gaps are shorter than one upload segment never becomes resident.** The background upload takes a table in short row-id segments and only in an idle window; a segment has a fixed cost no smaller segment escapes (the statement's parse and bind, and DuckDB's scan set-up over the table's row groups — measured 2026-09-20: about 0.4 ms on an M4 Max, about 1.5 ms on an x86 box), so a workload that never pauses longer than that has every segment interrupted and the set stays off the device | Not a wrong answer and not a slowdown: every statement is answered by DuckDB at native speed, which is what rule 1 asks for. The size follows the yield down to a floor derived from this machine's own segment cost — or, until two sizes have landed and a halving can be priced at all, to 1/32 of the default — and at the floor the manager reports it rather than grinding finer (`con._manager.progress()[tag]['starved']`, with the window it measured; `GPUDB_RESIDENCY_TRACE=1` prints a line per attempt). To get the set resident anyway: `residency='eager'` (one upload on first sight, for a script that knows its workload), or a pause in the statement stream long enough for one segment. `docs/TRANSPARENT_DESIGN.md` §5.5 |
| **A statement is re-decided by measurement, not only by the bounds.** The wrapper times native once per template after its first three rewritten runs (on a side cursor), declines the template when the rewritten runs are not faster, and re-measures every 60 s | "Two modes of a short kernel" (§9.1, measured 2026-09-18): a 2 ms exact GROUP BY kernel on an M4 Max runs at 2.0 ms or at 6.5 ms depending on what the rest of the *process* is doing — DuckDB's idle worker threads waking every few milliseconds put it in the slow mode, `SET threads TO 1` restores the fast one, and 15 sleeping Python threads are enough to flip it either way. It is the SoC's power management, not the extension (same on `main`, with or without the store, in the embedded CLI without Python), and a bandwidth-bound kernel is unaffected. So a shape that wins 1.8× in the fast mode can lose (0.85×) in the slow one, and no static threshold captures that. The user's own statement is never the experiment. |
| **The memory budget.** `memory_budget` (bytes, or `'16GB'`; `0` / `'unlimited'` removes the cap; `GPUDB_MEMORY_BUDGET_MB` overrides the default) defaults to a quarter of unified memory on Apple silicon and half of device memory on a discrete GPU — until a backend reports its device memory, a discrete GPU gets the smaller of a quarter of host memory and 8 GiB, so set it explicitly there. A set that does not fit — larger than the budget, or nothing evictable — is **not uploaded** and its statements run on DuckDB (`reason == "memory"`); the set is asked about again only when something that could change the answer changes — a write, the budget, an eviction that freed room, or 30 s. An upload the DEVICE refuses (out of memory although the budget allowed it) is the same answer under a different name: the set is dropped, nothing of it is left resident, and it is not retried on the next statement. A set is never placed on the host instead — a host-resident exact set answers from the CPU reference, which is slower than DuckDB | The pre-upload estimate is an upper bound by construction (lane widths from the DuckDB column types and, for a plain column, its own min/max from DuckDB's zone-map statistics — since stage C a lane is stored at the narrowest width its values fit, and the type alone was 2.4x the truth; plus a validity bit per row and lane, the key's sort cache and one scratch lane), which is what an admission rule needs. The truth afterwards is one physical thing counted once: `con.memory()["bytes"]` = the distinct columns of `gpu_store_columns()` plus every set that holds columns of its own. The per-set `bytes` in `con.memory()["sets"]` are what each SET costs and are NOT summable — a store-backed set is a view over shared columns, so summing them counts a shared column once per reader, and `gpu_residents().bytes` alone reports 0 for every such set by design. Eviction goes by value per byte, never a set an operator is using, a source of another resident set, or that source's store columns. Sets uploaded by hand count toward the total and are never evicted. Worked example: at TPC-H SF50 (300M-row sets of 9–15 GB arriving back to back, `GPUDB_MEMORY_BUDGET_MB=40000`) 10 of 22 queries landed on the device and six were refused as `memory`. A benchmark that uploads a new set every few seconds needs more room than a session does. Working memory an operator needs transiently (a reduce's scratch) is not resident and no budget over resident bytes can hold it: a statement that fails for it refuses its sets, and where the backend reports the shortfall the budget holds that much back from then on. `scripts/budget_gate.py` is what pins all of this. |
| **What a set is worth is learned, so the first minutes under a tight budget cost a re-arrangement.** Under a budget smaller than the working set the wrapper keeps the sets that save the most DuckDB time per byte (§5.5), and the saving of a template is only known once the measured rule has both its times — which is after its third rewritten run. Until then a candidate nobody has measured is priced at the median of what is resident | Measured at TPC-H SF10 with the 22 queries in a loop at an 8 GiB and a 12 GiB budget: loop 0 is cold, loops 1–3 pay the uploads of the sets the first real measurements ask for, and from loop 4 on the resident population does not change again and nothing more is evicted — steady-state loop 0.57–0.81 s against least-recently-used's 0.84–0.90 s at 12 GiB, with two more of the 22 queries on the device. A session that runs each statement once and never returns learns nothing and behaves as it always did. |
| **`residency='eager'` does its residency work inside the statement that asked for it** — the upload, and any eviction the budget needs. A single statement in the first loops of a cold eager run therefore reads in seconds | It is what the mode is for: scripts that know their workload and want the set now (`tpch_coverage.py` and the thrash probe both use it). The shipping default is `residency='background'`, where the uploader runs in idle windows on its own thread and `_make_room` is never called from a statement's thread; measured over 45 loops at a 12 GiB budget, the slowest statement after the cold loop was 172.8 ms on `main` and 177.1 ms on this branch, both of them a query that runs on DuckDB either way. |
| **A refused candidate must cost nothing, and this is counted rather than assumed.** `memory()["evictions_wasted"]` is the number of evictions made for a candidate that was then declined | `_make_room` snapshots, plans, and only then executes, so a refusal happens before anything is dropped; the one way the counter can move is a `gpu_drop_*` that itself fails, after which the caller re-plans against a fresh snapshot (three plans, then a refusal). It measured 0 in every thrash loop at both budgets, in both residency modes. The earlier revision, which decided and dropped in the same pass, tore down ~1.9 GiB in one loop for two candidates that both ended up native. |
| **A join's result is still a copy.** A device key join (§4.8) reuses one resident set per base table, but an uploaded join (§4.13) is one set per distinct FROM clause and lane list, holding `join rows × lanes × 8` bytes | Columns are shared per table since the store (§5.10), and lanes are stored at the narrowest width their values fit (`docs/RESIDENT_COLUMNS_DESIGN.md` §6) — the 22 TPC-H queries at SF10 hold 18.7 GiB where they held 44.9 (22.7 after narrow lanes, then 18.7 once a key lane with few distinct values stopped keeping a sort cache). Join results were 17.8 GiB of the 22.7, because a join's rows are in the join's order and not the table's; sharing them is stage D of the storage design, which no release carries. |
| **Uploading a column costs 65–85% more since lanes are stored narrow** — `lineitem`'s seven-lane store upload at SF10 went from 112 ms to 195 | Choosing the width needs a second pass over the lane to pack it. It is paid once per column, in the wrapper's idle background segments and never on the query path, and it buys a store 2.3× smaller and kernels that read a quarter of the bytes on every statement afterwards. |
| **The direct grouped reduce serves few-group keys only**, and is backend-private: at most 512 distinct key values (`GPUDB_METAL_DIRECT_MAX_GROUPS`), and the threadgroup slab holds `groups × (6 × payloads + 1)` 32-bit words in 30 KiB — 512 groups with one payload, 404 with three, 247 with five. It is taken only at `groups >= 3` and `rows × (payloads + WHERE terms) >= 6,000,000`. `min` / `max` are exact on it for a payload lane stored at 4 bytes or fewer; a wider payload with `min` / `max` asked for keeps thread-private accumulators while they hold it (32 slots) and takes the sort path above that. Not offered at all on a GPU below the `MTLGPUFamilyApple7` family, or on a virtualised Apple GPU (a device whose name contains `Paravirtual`) | Every case outside these bounds is a hard decline to the sort path, which gives **the same answer** — same rows, same order, NULL-key group last — at 0.99–1.04×; only the speed of that one shape changes. Apple GPUs have no 64-bit atomics, so the slab is 32-bit throughout and the extremes are order-preserving u32 images, which is exact only up to 4 bytes. The paravirtual deny entry is written from evidence: on a hosted macOS runner ONE refused pipeline build left that process's Metal compiler unusable, so the path asks the device what it is before asking it to compile anything. `gpu_last_stats()` prints `path=direct` / `path=sort`. |
| **A statement reads at most 12 distinct resident lanes** on Metal's fused aggregate without `GROUP BY` (§4.12); payloads and predicate columns share the slots, so TPC-H Q6 uses four. Above that the operator throws and the statement runs on DuckDB | Each lane is bound as one buffer pair (data + validity). Twelve slots cover every shape in the suite and in the gate; the alternative was an argument buffer holding GPU addresses, which nothing needs. |
| **Writes from another connection** (§5.9): on a file-backed database every committed write by any connection is noticed before the next rewritten statement (the database file and its WAL are stat'ed, 2–3 µs) and the resident sets are rebuilt; the row-count guard alone would miss an in-place `UPDATE`. On an **in-memory** database there is no file to watch: writes made through the wrapper's connection or its `cursor()`s are seen, and a write through a raw `duckdb` cursor is not — such a database falls back on the in-statement `gpu_assert_rows` guard, which catches a row-count change but not an in-place `UPDATE` | Use the wrapper's own cursors for writes, or a file-backed database. A read-only connection watches nothing because nobody can write the file while it is open read-only. A `CHECKPOINT` from another connection is indistinguishable from a write and costs one rebuild. |
| **When the rewritten statement itself fails**, the wrapper runs the user's ORIGINAL statement on DuckDB and the template stays native afterwards (`reason == "error"`, the text in `last_rewrite()["error"]`) | Rule 2: a device allocation that fails at query time, a set dropped behind the wrapper's back or a defect must not change the answer; if DuckDB raises too, it is DuckDB's own error for the user's own statement. A user interrupt is not retried. Staleness is separate and always re-runs natively (`GPUDB_STALE:`). |
| **The `gpudb` shell is a client, not a DuckDB CLI.** It runs statements, dot-commands and files and nothing else: no `.mode` / `.output` / `.import` / `.excel`, no `SELECT` completion, no `.shell`. One consequence of how it renders: a result above 9999 rows shows the Python client's footer (`? rows … (>9999 rows, 40 shown)`) rather than the C CLI's exact count, because the relation streams | It is the terminal client for the transparent path (`docs/TRANSPARENT_DESIGN.md` §6), not a replacement for `duckdb`; the two can be used side by side on the same file. The rendering is DuckDB's own (`rel.show()`), so the box, the types and the row footer are whatever the Python client prints |
| **`con.sql()` decides like `con.execute()`, with two differences a lazy relation forces** (`docs/TRANSPARENT_DESIGN.md` §3.3). The measured rule 1 fires for `sql()` too, but from side cursors on both sides and only from a template's third sighting, since the statement has not run when the call returns. The operator's output-size check reads `rows_out` after a run, so a template first seen through `sql()` gets that check on its first `execute()` instead | Both calls share one decision, so a verdict measured through either applies to both. What cannot be moved inside the call is an error the relation raises when it is finally READ — including a write that commits between `sql()`'s own guard check and the caller's first fetch. The wrapper runs the rewritten statement's `gpu_assert_rows` guard on a side cursor before handing the relation over, which puts the common staleness case back inside `sql()`; for the rest, `execute()` on the same statement re-runs the original natively, and that is what the shell's `recover()` does |
| **The Python package's distribution name is `duckdb-gpudb`; the import name stays `gpudb`.** `gpudb` on PyPI is Kinetica's client, so the two cannot both be installed under that distribution name; the import name clashes only for someone who has both | `python/README.md` documents how the wrapper finds the extension (an explicit `extension=` path, `GPUDB_EXTENSION_PATH`, a local build next to a source checkout, and finally the copy DuckDB itself installed). The DuckDB community-extension name `gpudb` (`INSTALL gpudb FROM community`) is a separate namespace and is unaffected. The wrapper is Python: the join, expression and split lowering lives there, while the pure `gpu_rewrite_ast` function is language-neutral and carries no client of its own. |
| `gpu_join_materialize` (§4.8) joins only on a build lane that is unique among its non-NULL cells, inner equi-join on one BIGINT lane per side | It materialises fact-to-dimension joins as a new exact set (a subset of the probe rows with build columns gathered), which is only the join's result when no probe row can match twice. A duplicate build key fails with `build key not unique`; many-to-many, outer / semi / anti joins stay on the v0.5 fused functions or native. Composite and VARCHAR join keys run native. Implemented on CPU (the reference), on Metal and on CUDA, on by default on both GPUs (`join_supported()` reports the GPU side); under `GPUDB_CUDA_EXACT=0` a CUDA build falls back to the CPU reference. The joined set holds `rows_out × lanes × 8` bytes of device memory and goes stale when either source set is stale, dropped or replaced. |
| Joins on the transparent path (§4.8 / §4.13): inner equi-joins onto unique keys are materialised on the device; other INNER / LEFT joins of base tables tied by equalities (many-to-many, `USING`, composite or non-integer keys, extra `ON` predicates, self joins, keys or expressions mixing two tables) are answered from an upload of the join's result. `A RIGHT JOIN B` is normalised to `B LEFT JOIN A` (§4.21) and goes the same way, and a derived table as a join input is folded in and joined like any other input. `FULL` joins, `SEMI` / `ANTI` join syntax, `NATURAL` joins (`shape`, detail `INNER NATURAL join`), a `USING` clause over a derived table that renamed the join column (`shape`, detail `JOIN ... USING` — plain `t1 JOIN t2 USING (k)` over base tables is rewritten), cross products, more than six tables, and a join whose result exceeds four times its largest table run native | The device join reuses one resident set per base table across statements and rebuilds in milliseconds; an uploaded join is one set per distinct FROM clause and lane list and is re-uploaded (in idle-time row-id segments of the leftmost table) when any joined table changes. Staleness is guarded per base table in both cases — by the table's own set, or by a `gpu_note_rows` sentinel. An aggregate without GROUP BY is rewritten over a join at any size; on a single table native's filter-and-sum wins below the row bound (TPC-H Q6 at SF1: 0.67–0.71×), so it is left alone there. |
| Expressions (§4.10): a deterministic row-local expression over ONE table's columns may be an aggregate's argument, a GROUP BY key, or a `WHERE` term (`OR`, `LIKE`, function predicates, column-vs-column included). `random()` / `now()` / `nextval()` and other non-`CONSISTENT` functions, session-state functions, user macros, subqueries outside a WHERE term (§4.18), windows, lambdas, and DOUBLE-typed payload expressions (`sum(v / 2)`) run native; an expression mixing columns of two joined tables makes the join an uploaded one (§4.13) | DuckDB evaluates the expression during the upload, so semantics are native's; the expression becomes one more lane of the resident set, identified by a hash of its SQL. Every distinct expression — including every distinct literal inside one, such as a LIKE pattern — is its own lane and its own upload: repeated statements benefit, an ad-hoc stream of new patterns stays native (at most 16 literal variants per statement template are tracked). Few-group shapes over a single table (TPC-H Q1) stay native under the `min_groups` threshold unless the key is VARCHAR and enough payloads are computed. The lowering lives in the Python wrapper; the pure `gpu_rewrite_ast` function is language-neutral and carries no client of its own. |
| Expressions over aggregates and compound `HAVING` (§4.11) — `sum(a) / count(*)`, `max(p) - min(p)`, `HAVING sum(a) > 10 AND count(*) > 5`, `ORDER BY` an expression of aggregates — run as a device GROUP BY plus a projection DuckDB evaluates over it. DOUBLE aggregates, `DISTINCT` aggregates with a `FILTER`, windows and subqueries in the select list keep the statement native (`FILTER` on sum / count / min / max / avg, `count_if`, `bool_and` / `bool_or` are rewritten, §4.19) | The inner GROUP BY returns every group (the plain form), so its thresholds are the plain form's: statements whose inner result is large run native. The per-statement measurement (row above) is the backstop. |
| `count(DISTINCT x)` (§4.17): one DISTINCT column per statement, beside `sum` / `count` / `min` / `max`; `avg` in the same statement, `sum(DISTINCT)` and two different DISTINCT columns run native | The device groups by (keys, x) and DuckDB re-aggregates the pairs, so the form is bounded by the number of pairs: native above 100K pairs, above 20K under a `WHERE`, and under a `WHERE` that keeps less than 5% (measured 0.39–0.51× at 700K pairs). |
| **`avg` over a `DECIMAL` payload needs an extension that provides `gpu_avg_decimal`.** With one, it is exact on every platform. Against an extension too old to provide it, the column is derived in SQL instead, and the wrapper declines the shape (`shape`, the detail naming `long double`) only where that derivation is not native's own arithmetic — that is, where `gpu_build_info()` reports `avgf=` anything but 53 | DuckDB finalises `avg` as a `long double` quotient, which is a plain `double` on arm64 and 80-bit on x86-64, and SQL has no 80-bit type — so a SQL derivation matched native only on arm64 (982 of 5000 groups differed on x86). `gpu_avg_decimal(sum HUGEINT, count BIGINT, scale BIGINT)` does the division in C++ in the host's own `long double` (#160). The exact GROUP BY already returned the sum as `HUGEINT`, so nothing in the table functions or the identity tags changed and the fix is additive across version skew. Verified against native over 401 groups: the SQL derivation differs on 85, the scalar on 0 |
| `DATE` / `TIMESTAMP` payloads take `min`, `max` and `count` only; `HAVING` or top-k on such an aggregate stays in the SQL DuckDB runs over the result | The lane holds days / microseconds since the epoch; the rewritten select list types the value back. |
| `GROUP BY` takes one to eight keys. Up to three integer / DATE / TIMESTAMP keys are packed into one 64-bit key; four to eight keys, or any VARCHAR / DECIMAL component, use a hashed tuple with a dictionary (DOUBLE, UBIGINT, HUGEINT keys decline) | A wide key's dictionary holds one text tuple per group in host memory and is sent through `gpu_resident_dictionary` for the plain form (every group comes back anyway); a device HAVING / top-k decodes only the surviving keys with `gpu_resident_dict_component` (TPC-H Q10: 17.5 → 4.0 ms, against 0.46× for the plain form that has to join the whole dictionary). |
| The plain form over a join runs native above 1M groups returned, and above 300K groups when the device reads fewer than 16 rows per group returned | Measured 2026-09-19 (`transparent_gate.py --ctes`): a join returning 664K–729K groups out of 6M lineitem rows measures 0.98–1.00× on five cells, while the same statement at 195K–200K groups measures 1.05–1.11× and at ~100K groups 1.15–3.18×. These are the bounds for a statement whose groups the CLIENT fetches; an inner statement has its own (the row below). |
| **An inner statement** — a `GROUP BY` the nested pass (§4.14) lifted out of a bigger statement, whose groups DuckDB reads out of the table function and consumes itself — is decided by the output-size bounds only when its consumer does not reduce it. When the whole statement returns at least 4× fewer rows, the device is reducing at least 7 rows into each row it returns, and there are at most 2M groups, the group caps and the selectivity bounds do not apply | Measured 2026-09-19 (`transparent_gate.py --inner`, SF1): the same cells wrapped in four consumers. Every cell below 1.0× is at 2.9–4.0 rows read per group returned (0.44–0.97×); the band at 5.4 measures 1.05–1.34×; every cell at 7.5 or more measures 1.29× or better. The join-back consumer, which returns every group to the client, wins and loses exactly where the client-facing plain form does, which is why the reduction is a condition. `last_rewrite()["detail"]` names the rule in both directions. |
| **The row floor counts the largest table the answer depends on**, including one that only a §4.18 subquery lane reads — not only the statement's own `FROM` | A statement over a small table whose `WHERE` holds `NOT EXISTS (SELECT … FROM <big>)` makes native read `<big>` on every run while the device reads it once, into the lane. 48 cells over five outer tables (10K to 1.5M rows) with `NOT EXISTS` / `IN` / correlated-scalar lanes measured 1.22–31.44×, none below 1.0× (2026-09-19, `transparent_gate.py --lane-floor`). TPC-H Q22 at SF1 is the case: 150K `customer` rows, a lane over 1.5M `orders` rows, 10.2–10.6×. |
| A statement may aggregate up to eight different payload columns (§4.9); `DOUBLE` / `FLOAT` payloads and `DECIMAL` wider than 18 digits decline per payload; an aggregate over an expression (`sum(a * b)`) is a computed lane | Extra payloads are BIGINT lanes of the same resident set, reduced by `gpu_groupby_exact_multi` — on Metal with the mask and the grouping shared between them, on other backends as one pass per payload (the generic default). Every extra aggregate is another output column on both sides, so the plain form with several payloads runs native under a `WHERE`, above 50K groups on a single table and above 20K groups over a join; HAVING and top-k are unaffected. |
| Subqueries, derived tables, CTEs and UNION arms (§4.14): a SELECT inside a statement is rewritten on its own when it is a transparent shape by itself; the enclosing statement stays on DuckDB. Subqueries that read another subquery / CTE, and correlated subqueries outside a WHERE term of an aggregating statement (§4.18), stay native | The inner SELECT has its own decision, thresholds, residency and staleness guards; any of them turning stale falls the whole statement back to native. The composed SQL is cached by exact statement text. |
| Subquery predicates (§4.18): `EXISTS` / `NOT EXISTS` / `IN (SELECT …)` / `NOT IN` / a correlated scalar subquery as a WHERE term of an aggregating statement. The subquery must be a plain SELECT over base tables: `LIMIT` / `ORDER BY` / windows / samples / derived tables / CTE references inside it, non-`CONSISTENT` functions, and `sum` / `avg` over floating columns inside it keep the statement native. Subqueries in the select list or in `HAVING` are not lowered | DuckDB evaluates the predicate per row during the upload and the result is a BOOLEAN lane, so every distinct subquery text (literals included) is its own lane and upload. Each table the subquery reads is guarded: a change to it makes the set stale and the statement runs native until the set is rebuilt — a subquery over a frequently written table keeps the statement native most of the time. |
| Views (§4.20): a view of the current catalog and schema is inlined as a derived table, after which the usual rules apply; views in other schemas, names that are both a table and a view, and views whose body is a set operation run native | The wrapper re-reads the definitions of the views a cached statement was built on before every run (~0.2 ms), so a redefinition from any connection is honoured on the next statement. The view's own tables are guarded like any base table. |
| CTEs (§4.22): a CTE that only projects and joins is spliced in at every reference (any number of them) and folded like a derived table, including as one arm of a join and including a CTE that reads an earlier CTE. A CTE that AGGREGATES is left in place on purpose — the nested pass (§4.14) answers it once on the device and DuckDB reuses that one result. Left as written: `WITH RECURSIVE`; `AS MATERIALIZED`; a body holding a function the computed-lane rules do not vouch for (`random()`, `now()`); a body with `ORDER BY` / `LIMIT` / `DISTINCT` / a window / a set operation; an arm of an outer join (its `WHERE` may not be hoisted above the join); an arm beside a subquery predicate; a CTE joined to itself | The splice is `python/gpudb/_ctes.py`, verified against the original with `DESCRIBE` (names and types) like §4.19 – §4.21; the fold of a join arm is `python/gpudb/_flatten.py`. A CTE joined to itself flattens onto the same unaliased table and stops binding — the DESCRIBE check catches that and the original text runs. |

### The size bounds, form by form

Every bound below is read off `python/gpudb/_thresholds.py` and
`Connection._decide_body`; the decline sentences are what
`last_rewrite()["detail"]` actually prints. One floor applies to every row:
**the statement's answer must depend on a table of at least `floor_rows`
rows** (default 1,000,000), counting the largest such table, a §4.18 subquery
lane's included — otherwise the statement declines with *the statement names
no table at or above the 1000000-row floor*.

"Aggregated columns" below counts **distinct payload columns**, not aggregates:
`count(*)` reads no column and adds nothing, and several aggregates of the same
column are one payload — `SELECT l_partkey, sum(l_quantity), count(*) FROM
lineitem GROUP BY 1` is a one-column statement and rewrites, while
`sum(l_quantity), sum(l_extendedprice)` on the same key is a two-column one and
declines with *191008 groups x 2 payload columns returned > 50000* (both
verified at TPC-H SF1).

Above that floor, the form decides:

| Form | Group floor | Output-size bound | Selectivity, under a `WHERE` |
|---|---|---|---|
| **plain** `GROUP BY`, one aggregated column | 1,000 distinct keys (*3 groups < 1000*) | 300,000 groups; 50,000 under a `WHERE` | at least 0.5 (*selectivity 0.13 < 0.5 for the plain form*) |
| **plain** `GROUP BY`, two to eight aggregated columns | the same 1,000 | 50,000 groups — and under a `WHERE`, native at 1,000 groups or more (*plain form with 2 payload columns under a `WHERE`*). Below 1,000 groups the multi-column bound is not consulted at all, which is the gap the `VARCHAR` exemption in the bullet below goes through (TPC-H Q1) | — (at 1,000 groups or more the `WHERE` declines it outright) |
| **`HAVING`** on the device | the same 1,000, with **no `VARCHAR` exemption** — that one is the plain form's | none | at least 0.3, and at least 0.2 from 100,000 groups up |
| **`ORDER BY … LIMIT k`** (top-k) | 100,000 distinct keys | none | at least **0.8** (*selectivity 0.50 < 0.8 for top-k*) |
| **over a key join**, or with a subquery lane (§4.18) | **none at all** — native has to run the join whatever the group count, so one group is admitted | plain form: 1,000,000 groups, and above 300,000 the device must also be reading at least 16 rows per group returned; 20,000 groups with two or more aggregated columns. `HAVING`, top-k, and a `LIMIT` that was not pushed as a top-k: none | plain form above 20,000 groups: at least 0.08. `HAVING` and top-k: none |
| **aggregate with no `GROUP BY`** | — (one group) | — (one row) | — | 
| **the inner statement** of a nested rewrite (§4.14, §4.23) | the group floor still applies | the output-size bounds are **replaced** — for a statement with ONE aggregated column — when all three hold: the whole statement returns at least 4× fewer rows, the device reads at least 7 rows per group returned, and there are at most 2,000,000 groups. With two to eight aggregated columns the multi-column row above is applied first and decides on its own: `SELECT max(q), max(p) FROM (SELECT l_suppkey, sum(l_quantity) q, sum(l_extendedprice) p FROM lineitem WHERE l_shipdate < DATE '1997-01-01' GROUP BY 1)` declines with *plain form with 2 payload columns under a `WHERE`*, while the same statement with `q` alone is rewritten | replaced under those same three conditions, and only for one aggregated column |
| **`count(DISTINCT x)`** (§4.17) | the 1,000, with the exemption relaxed: for a `VARCHAR` key, **one** computed-expression payload beside the DISTINCT is enough | 100,000 (key, value) pairs; 20,000 under a `WHERE` | at least 0.05, and then the form's own bound above |

Two bounds do not fit a column:

- **An aggregate with no `GROUP BY`** has one row out, so nothing about it is
  output-bound. Over a join it is rewritten at any size. Over a single table it
  needs **16,000,000 rows** *and* `rows × (1 + WHERE terms, counting at most
  three) ≥ 60,000,000` (*6001215 rows < 16000000 for an aggregate without
  GROUP BY*).
- **The `VARCHAR` exemption from the group floor applies to the plain form and
  to nothing else.** A `VARCHAR` key rewrites below 1,000 groups with no
  `WHERE` at all, and under a `WHERE` when at least two of the payloads are
  computed expressions and at least half the rows survive — native hashes the
  strings on every row and evaluates every expression on every row, and a
  resident lane does neither. This is what admits TPC-H Q1 (two `VARCHAR` keys,
  eight aggregates over expressions, 98% of rows kept) while the same two keys
  with plain column payloads decline at *6 groups < 1000*. The same three
  groups under a `HAVING` decline at *3 groups < 1000*, because `HAVING` is not
  the plain form.

Then the measured rule (the row above) overrides all of it in either
direction, and `last_rewrite()["detail"]` names whichever rule decided.

### Design notes — the `gpudb` shell (v0.7)

| Behavior | Reason |
|---|---|
| On Linux, a `Ctrl-D` typed **while a statement is running** is ignored; the shell stays at the next prompt. `Ctrl-D` at a prompt that is waiting always leaves, on every platform, and on macOS it leaves in both cases | `input()` hands the terminal to readline and hands it back when it returns, so a key typed while a statement runs reaches a terminal in canonical mode. There Linux's line discipline records `^D` not as a byte but as an end-of-file mark beside the input queue, and it clears that mark on the next change of `ICANON` — which is what the next `input()` does. macOS's libedit does not put the terminal back between calls, so the byte stays a byte and is read later. Stock Python reproduces both, in eight lines of `input()` in a loop (measured on both platforms, `docs/RESEARCH_NOTES.md` 2026-09-19); it is the platform's behaviour, shared with every other readline client, not the shell's. `Ctrl-C` is a signal rather than a key, and has a window of its own — the row below. |
| A `Ctrl-C` typed at a waiting prompt in the same instant as the character before it can appear to do nothing, and then throw away the NEXT line typed instead of the one it was meant for. Pressing it again, or simply typing on, always clears the line | The same `input()`, a different mechanism: CPython's readline waits for a key in a `select()` and looks for a signal only where that `select()` returns `EINTR`, so a SIGINT arriving while readline is still digesting the previous keystroke stays pending with nobody reading it, and is raised at the next byte. Stock Python reproduces it with nothing of ours in it — 32 of 60 rounds silent when the `^C` follows the echo of the last key immediately, 0 of 60 when it follows a fifth of a second later, GNU readline 8.2 on a loaded Linux runner (`docs/RESEARCH_NOTES.md` 2026-09-19). A hand on a keyboard is never that fast; the shell's own pty test was, which is how this was found. |

### Type support (v0.3.0)

| Aggregate | Supported input types | Notes |
|---|---|---|
| `gpu_sum` | `BIGINT`, `DOUBLE` (and `INTEGER`/`SMALLINT`/`TINYINT` via DuckDB's implicit widening to the `BIGINT` overload) | Smaller integer types carry no dedicated overload — they widen to `BIGINT`, which is why the result type of `gpu_sum(INTEGER)` is `BIGINT`. `BIGINT` sums wrap on int64 overflow where native `sum()` promotes to `HUGEINT`. |
| `gpu_min` / `gpu_max` | `BIGINT`, `DOUBLE` (and smaller integers via implicit widening) | `DOUBLE` overloads added in v0.3.0. NaN ordering matches native DuckDB: NaN sorts greatest, so `gpu_max` over a NaN-containing group is `NaN`, `gpu_min` prefers finite values, and an all-NaN group is `NaN`. |

**Casting gotchas (all three aggregates):** `HUGEINT`, `DECIMAL`, and `FLOAT` arguments implicitly cast to the `DOUBLE` overload — values beyond 2^53 lose integer/scale precision where native aggregates are exact, and the result type is `DOUBLE` (native preserves `HUGEINT`/`DECIMAL`). `VARCHAR` arguments are a binder error (native `min`/`max` do lexicographic comparison). Use native aggregates where those types matter.

## Resolved issues

| Issue | Fixed in |
|---|---|
| A write from another connection that kept a table's row count — an in-place `UPDATE`, or a delete and an insert of the same size — passed the `gpu_assert_rows` guard, and a rewritten statement answered from stale values | 2026-09-18 (`main`, transparent path) — the wrapper now stats the database file and its write-ahead log before every rewritten statement (2–3 µs): any committed write drops every resident set and the statement runs native while the next one rebuilds. Not covered: an in-memory database written through a raw cursor (see the v0.7 table above) |
| Metal radix sort (the sorted build cache behind the v0.5 fused / row joins, and the v0.6 GROUP BY / top-k) produced an unsorted result for key sets whose min and max agree on a byte that other keys differ in — e.g. TPC-H `l_returnflag`/`l_linestatus` packed to one `BIGINT` (`0x4146`, `0x4E46`, `0x4E4F`, `0x5246`: min and max share low byte `0x46`, `0x4E4F` does not) came back as 66,085 groups instead of 4 — and, less exotically, any dense key range whose min and max share a low byte, such as `0..256`, `0..65536` or `0..2^20`; a Metal join against such build keys could miss matches. Affects the **v0.5.0 Metal binary** for such key sets (CUDA unaffected; ranges like `1..150000` or TPC-H `orderkey`/`custkey` differ in every low byte and were not hit). The same heuristic existed in a second copy inside the non-resident Metal `GroupByAggregator` radix path (C++ API / `gpudb-groupby-bench` only, not reachable from SQL) and is fixed there too | v0.6.0 — the pass-skip heuristic compared min and max byte-by-byte and skipped every pass where they matched; that is only valid for bytes above the highest differing byte (the prefix every key in `[min, max]` shares). Now: all passes at or below the highest differing byte run. Regression coverage in the unit suite and in both parity harnesses (`join_parity_check.sh`, `groupby_parity_check.sh`) |
| Metal v1 `HashJoinProbe` lost a small number of matches on GitHub's macOS runner (`Apple Paravirtual device`): 199,973 vs 199,998 on a 50k×200k join | v0.5.0 — the slot-lock tables spun on a locked slot for a bounded number of attempts (a GPU gives no cross-threadgroup forward-progress guarantee, so the spinner could give up and silently drop its row), read another thread's key through relaxed atomics, and chained init → build → probe in one compute encoder with no memory barrier. | CUDA v1 `HashJoinProbe` (operator-level, `gpudb-hashjoin-bench`) emitted every build row for duplicate build keys, diverging from the CPU reference and the header contract (first build row wins) | v0.5.0 — one slot per key, `atomicMin` on the smallest build index. Behaviour change only for callers relying on the old multimap output of the v1 probe; the v0.5 fused joins carry full multiplicity by design and are unaffected |
| `gpu_min/gpu_max(DOUBLE)` leaked the fold identity (`+inf`/`-inf`) on all-NaN groups, and `gpu_max` dropped NaN where native returns NaN | v0.3.0 — caught by pre-release adversarial review, fixed before the overloads ever shipped: f64 min/max folds now use a NaN-aware total order matching native (NaN sorts greatest) |
