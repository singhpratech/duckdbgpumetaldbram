Plain DuckDB SQL on the GPU

On Apple Silicon (Metal) and NVIDIA (CUDA). Write the SQL you already write: the GPU answers a statement when that is measured faster, and DuckDB answers everything else, with the same rows either way.

gpudb is a DuckDB community extension, a Python package and a gpudb shell. No hints, no schema changes, no query changes.

Python and the gpudb shell 
$ pip install duckdb-gpudb
Any DuckDB 1.5.5 or later client, for the gpu_* functions

How a statement reaches the GPU

The extension alone gives the gpu_* functions. Plain SQL reaches the GPU through a client that sees the statement before DuckDB plans it.

  1. You write ordinary SQL

    Through the gpudb shell or gpudb.connect() in Python. duckdb.connect becomes gpudb.connect(); the SQL is untouched.

  2. DuckDB parses, gpudb rewrites

    Before DuckDB plans it, the statement goes through DuckDB's own parser (json_serialize_sql) and a pure function in the extension (gpu_rewrite_ast). No plan surgery, no C++ API.

  3. Resident columns answer it

    A shape measured to win, over a table past the 1,000,000-row floor, runs on columns already in GPU memory. Tables become resident in the background, between your statements.

  4. Everything else is DuckDB

    Any other statement runs on DuckDB unchanged, at DuckDB's speed. Any error on the rewritten path re-runs your original statement on DuckDB.

Two rules

Never a different answer than DuckDB

A rewritten statement returns what native DuckDB returns: the same rows, the same order where native guarantees one, the same column names and the same column types. Integer and DECIMAL aggregates are bit-exact, with 128-bit sums on the device.

Where “the same as native” is not definable, the shape is never rewritten: sum(DOUBLE), which DuckDB itself computes in an order-dependent way, and an ORDER BY … LIMIT k whose first k rows tie, which goes back to DuckDB.

Never slower than DuckDB

Not on average: per statement, per shape, per size. Which shapes may be rewritten comes from bounds a gate measures against native before a release, and the losing measurements stay published.

Your machine is not the gate's, so the decision is taken again there. After a statement template's first three rewritten runs, the wrapper times the native form once on a side cursor in your own process, hands the template back to DuckDB if the rewritten runs were not faster, and measures again every 60 seconds.

Where it stays on DuckDB

  • At SF10, three queries. Q2 and Q20 each read a subquery from inside another subquery; the inner statement is correlated and does not bind on its own, so there is nothing to hand the device. Q16's inner GROUP BY declines on its own threshold; forced past it, Q16 measures 0.02–0.08×.
  • At SF1, five. Those three, plus Q6 and Q11, which sit below the measured size floors at 6M rows. The CUDA machine declines the same five at SF1.
  • Each of them runs on DuckDB unchanged, at DuckDB's speed.

Results at or below 1.0×

  • Q11 at SF10 on Metal straddles parity. A 6–7 ms statement: 1.06× through execute() and 0.92× through sql() in the timed run, 1.06× and 0.89× in two immediate re-runs of the same build. This is the case the per-process measured rule exists to settle.
  • TPC-H Q1 on CUDA first measured 0.96× and 0.98× on the release build: a few-group key was being answered by sorting the whole column. CUDA got a direct grouped reduce for such keys, and Q1 now measures 1.99× through execute() and 2.07× through sql().
  • A predicate that matches nothing, on CUDA at SF1: 0.76 ms on the device against 0.21 ms native, 0.28×. DuckDB skips the table through its zone maps; the measured rule declines it after one run.

Every per-query table and the commands that take the runs again are in BENCHMARK.md and the reading guide.

Where these lose, it is published too. A GROUP BY with a handful of groups is a native win on Metal (0.56–0.65× at SF10–SF50, a tie at SF1). Whole-column min/max on stored tables is a native win, because zonemap statistics answer without scanning. A one-time upload breaks even after about 100–150 repeated aggregate queries. The CUDA all-groups row is bounded by copying 24 bytes per group over PCIe, which unified memory does not pay.

What runs where

On the GPU
Aggregating statements over tables past the 1,000,000-row floor: sum, count, min, max and avg with or without GROUP BY, WHERE filters, HAVING, ORDER BY … LIMIT k, DISTINCT and count(DISTINCT), joins, EXISTS / IN subqueries, CTEs, views and derived tables.
On DuckDB
Window functions, sum / avg over DOUBLE, median / stddev, prepared-statement parameters, statements inside an explicit transaction, tables under the floor, a handful of groups, and sets over the memory budget.

A statement that stays on DuckDB returns the same answer at DuckDB's speed, in the same session; nothing fails. Full list

Three ways to use it

All three talk to the same extension and the same resident columns.

Python: import gpudb

For applications, notebooks and pipelines. gpudb.connect() takes the same arguments as duckdb.connect, anything it does not define is delegated to the underlying DuckDB connection, and last_rewrite() says what happened to the last statement.

The Python guide

python
import gpudb

con = gpudb.connect("my.duckdb")
con.execute("SELECT k, sum(v) FROM t GROUP BY k").fetchall()
con.last_rewrite()                # what happened to that statement

The gpudb shell

For exploring and ad-hoc SQL. Under every result is one line: where the statement ran, why, and how long it took. .gpu prints the whole record including the SQL that actually ran, .gpu off turns the path off for a comparison, and .residents and .memory show what is on the device.

The shell guide

shell
gpudb                             # in-memory database
gpudb my.duckdb                   # a file
gpudb my.duckdb --readonly        # nobody writes while you look
python -m gpudb                   # the same entry point
the footer
GPU (plain: the resident GROUP BY) · 3.3 ms
DuckDB (threshold: 7 groups < 1000) · 5.0 ms
DuckDB (not_resident: the resident set is not ready yet) · 12.0 ms

The gpu_* functions, in any DuckDB client

Full manual control from any client in any language, and the only route from the stock duckdb CLI: DuckDB's stable C extension API has no hook that sees a statement before it is planned, so there LOAD gpudb gives the functions, not the rewrite. Upload a column once, then ask it many times.

The resident model

duckdb
INSTALL gpudb FROM community;
LOAD gpudb;

CREATE TABLE sales AS
  SELECT (range % 1000)::BIGINT AS store, (range * 7 % 10007)::BIGINT AS amount
  FROM range(10000000);
SELECT gpu_upload_pair('sales_by_store', store, amount) FROM sales;   -- resident, once

SELECT * FROM gpu_groupby_sum_resident_topk('sales_by_store', 5, 'desc');
-- (282, 50037056, 10000) … top 5 stores by sum(amount): (store, sum, count)

SELECT gpu_last_stats();
-- op=groupby_sum_resident_topk backend=Metal reason=Hot_GpuAlwaysWins
--   rows_in=10000000 groups=1000 rows_out=5 wall_ms=39.568 kernel_ms=17.752 transfer_ms=0.000

pip install duckdb-gpudb
Python 3.9 or later and the duckdb module 1.4 or later. On Apple Silicon and x86-64 Linux the platform wheel carries the extension too, so it is the whole install; the Linux wheel is the CUDA-enabled build and bundles its own libgomp.so.1. Elsewhere it installs the wrapper alone and the extension comes from the registry.
INSTALL gpudb FROM community
Any DuckDB 1.5.5 or later client, signed, no flags. On Linux the registry binary may be a CPU-only build that reports compiled=cpu: for CUDA, use the pip wheel, the release binary or a build from source.
Release binary
Built against the stable C API v1.2.0, so it loads in any DuckDB 1.2 or later, started with -unsigned. On Linux it needs libgomp.so.1 (apt install libgomp1).
Which binary do I have?
